# Billing meters

Meter names use `<entry>.<object>.<action-or-unit>`, with entries `qq_protocol`, `qq_official`, `desktop`, and `bili`. Counts use `count`, token usage uses `tokens`, durations use `seconds`, and device gauges use `seats`. Each event has a tenant-scoped idempotency key that identifies the underlying operation; retries must reuse it. Gauge values represent the current value, not a delta. Event attributes contain identifiers and metadata only, never credentials or message content.

The agent reports accepted inbound messages, successful sends and session reconciliation through the authenticated Relay batch endpoint; the Bilibili bridge reports browsing and draft creation. The Relay records actual token usage atomically with wallet settlement. Custom upstreams also record token usage, with zero platform wallet charge. Chat and memory-consolidation model calls carry the originating entry, including archived chats whose channel is now disabled. Supervisor lifecycle checkpoints record hosting duration, and the desktop gateway records seat gauges and device online duration (overlapping connections for one device count once). Clients cannot submit server-owned token, hosting, or seat meters; their idempotency keys occupy a separate server-derived namespace. Metering records usage without introducing prices. Entitlements default to off and unlimited; administrators can configure off, soft, or hard enforcement.

Client count events are self-reported telemetry, not authoritative payment records. The Relay key fixes the tenant, and any explicit `attrs.platform` or `attrs.chatKey` must match the declared entry. Missing attributes remain compatible, and disabling an entry does not reject historical retries. A key holder can still invent distinct event IDs and counts within its own tenant; these can affect its usage or configured quota, but cannot debit the wallet. Legacy LLM requests and model-connectivity probes without attribution still use the existing wallet/ledger path with `entry=NULL`; they are not assigned to one of the four entries by guesswork.

Failed final duration checkpoints retain their original stop time for retries. Failed token/meter settlement rolls back wallet and ledger changes; the request fails and releases its reservation instead of reporting a successful charge. Upstream error payloads are not reflected to clients because they may contain credentials.

Desktop online-duration retries retain the original interval end and idempotency key, including when a provider commits an event and then throws. After that interval is acknowledged, the gateway accounts for later elapsed time separately. For an ended connection, one flush drains both an older uncertain interval and the final tail, stopping immediately if either write fails; normal shutdown therefore does not leave a payable tail after the retry succeeds. Pending online-duration intervals remain in memory. A manager crash, or shutdown while the ledger remains unavailable, can lose an uncommitted interval and requires reconciliation.

An active Relay request retains its wallet reservation even when a continuously producing stream outlasts the reservation TTL. Available balance includes that active hold; completion must settle a held reservation successfully before emitting `[DONE]`. Entry attribution remains the value captured at request admission. Active-hold protection is in memory and assumes a single manager per database; after a crash, abandoned holds still expire by their stored TTL. This does not recover usage lost in a process crash or automatically repair historical missing charges.

Chat-completion response bodies (platform/custom, JSON/SSE/error) have a cumulative raw-byte budget. `CLOUD_UPSTREAM_MAX_RESPONSE_BYTES` defaults to 8 MiB and is clamped to 16 KiB–64 MiB. Exceeding it closes the upstream immediately and returns a generic error without `[DONE]`. Complete SSE events accepted before the limit are settled using reported usage or the existing estimate. EOF before any complete output, valid usage, or `[DONE]` releases the hold, including streams containing only role or finish metadata. A complete empty response and valid zero usage retain their normal settlement semantics. Incomplete or over-limit bytes are excluded from delivered output.

Model discovery has a separate 1 MiB response limit and an eight-second absolute deadline, including continuously producing responses. Discovery failure retains the existing model-list fallback. Model identifiers containing the full configured upstream API key are filtered before reaching tenant APIs; valid identifiers remain available.

The Agent's 10,000-event threshold bounds its main in-memory queue, not retained event count. Excess events are atomically written into `meter-overflow/` and delivered in bounded batches with unchanged idempotency keys. Lost acknowledgements and restarts can cause retries but no duplicate server counts. Unreadable main spool data prevents startup and is preserved for recovery instead of being overwritten as an empty queue. Spill files are deleted only after successful Relay acknowledgement; monitor disk capacity during extended outages.

If a spool write fails, pending events remain in memory and a safe error category is logged; business processing is not rolled back. Recovery of storage allows a later write and replay, but a crash before either durable storage or Relay acknowledgement can lose those events. This is not an exactly-once guarantee across persistent disk failure.

Both the agent and Bilibili bridge require a JSON acknowledgement whose nonnegative integer `accepted + duplicates` equals the batch size. HTTP 200 alone is insufficient. Corrupt agent spill records are retained with an `.invalid` suffix for manual repair and excluded from delivery so valid events can proceed. Spool errors use safe categories instead of raw JSON parser or network error text.

A finite `desktop.device.seats` limit is a hard resource cap during pairing, including when the general enforcement mode is `off` or `soft`. A failed seat check does not consume the pairing code. The existing per-user device cap also applies. No usage charge is introduced.

Hosting seconds count supervised process time. The QQ entry receives its protocol process time and, when that entry is active, its shared Agent process time; the official QQ entry receives Agent time. The Agent run is attributed once, to the active QQ entry at run start, rather than being multiplied across desktop and Bilibili. A desktop-only Agent therefore has no hosting-seconds meter. Bilibili bridge time is recorded separately.

Hosting checkpoints persist the original entry, settled cursor and last observation. Each duration event and cursor update commit together. On startup and each periodic checkpoint, a checkpoint with a confirmed terminal `process_runs.stopped_at` is settled through that time; an unconfirmed old run is retained and logged for investigation without estimating an end time. Active runs also consult a persisted terminal time before charging elapsed time, so a missing terminal notification cannot extend billing past a confirmed stop. Runs without attribution checkpoints are counted in a startup warning and can be inspected by joining `process_runs` to `hosting_meter_checkpoints`. Historical runs are not backfilled. The normal checkpoint interval is five minutes; failed writes or an unconfirmed process end can leave a longer, unbounded period unresolved until it is investigated.

Within the current manager process, the Supervisor also retains the first confirmed end time for each run even if writing `process_runs` fails. A periodic checkpoint may settle to this observed end, and persistence retries preserve that time rather than substituting the retry time. Without a confirmed end, elapsed time only advances while the Supervisor still affirms a live, chargeable run: an observed exit, unconfirmed process group, lifecycle persistence error, or missing live service pauses advancement. A still-live process group is not declared stopped early. Restarting the process creates a new run and clears the previous observation. If the manager crashes before either the terminal record or meter checkpoint is persisted, the existing unresolved-history boundary still applies; this change does not automatically correct historical overcounts.

Gauge queries carry forward the most recent value before the requested window. With daily grouping, the carried value appears on the window's first UTC day; each later day with gauge observations reports its last observed value. Days without observations are not synthesized. Delta meters include only events inside the window. Each tenant has one effective override window per meter; setting another window replaces the previous rule.

If creating the initial hosting checkpoint fails, lifecycle observations are retained in order per run and retried on subsequent observations and periodic checkpoints. The first successfully read entry attribution is retained through retries, and a queued terminal observation uses its original end time. This also handles disabling the QQ entry while checkpoint persistence is unavailable. These pending observations are in memory: a manager crash before the initial checkpoint can still require manual reconciliation; no unknown attribution or end time is invented.

Migration v10 preserves all existing wallet, ledger, reservation and credential data. Historical ledger rows retain `entry=NULL`, and no historical meter events or charges are fabricated. Per-entry usage starts with new attributed events after upgrade; historical total usage remains available through the existing ledger queries.
