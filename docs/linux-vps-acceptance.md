# 养鱼 Bot Linux / VPS 测试与验收方案

- 编写日期：2026-10-29
- 适用项目：fish / 养鱼 Bot 一键托管平台
- 当前状态：NapCat P1 已进行本地实现和模拟测试；目标 VPS SSH 返回 `Permission denied (publickey)`，真实容器、扫码、模型对话及 HTTPS 控制台均未验收。P2 完整切换事务和 P3 全量恢复尚未完成；本文预期结果不代表通过。
- 第一轮目标：普通用户在 Linux 上创建自己的鱼，扫码登录 QQ，并在指定群完成真实对话；管理员能按用户管理实例。

## P2 真机验收待执行

SSH publickey 鉴权恢复后，在隔离测试实例上准备固定版本镜像、授权测试 QQ 和有效 LLBot Direct AT。先做一致性数据库、主密钥及 profile 备份，记录实例状态及镜像身份；禁止把二维码、凭据或 QQ session 写进验收报告。

| 编号 | 操作 | 必须记录的结果 |
|---|---|---|
| P2-01 | NapCat 在线时移除测试实例可用的 LLBot AT，提交切换 LLBot。 | `AUTH_TOKEN_REQUIRED`；旧容器 ID、端口和 Agent 运行未改变，原 QQ 仍可用。不能为了展示错误先停旧端。 |
| P2-02 | 提供有效 AT，分别完成 NapCat→LLBot、LLBot→NapCat；同一请求重复提交。 | 每次只有一个 operation；旧进程/容器确认退出后目标才启动；新 generation、端口和内部凭据隔离；实际 UIN 与预期一致且 OneBot 可用后才提交。 |
| P2-03 | 等待扫码超过启动超时；关闭弹窗、重新进入实例、继续扫码；更新二维码代次。 | operation 保持 waiting_qr；关闭弹窗不取消切换；新页面恢复同一 operation；旧二维码、旧实例响应不再显示。 |
| P2-04 | 使用另一获授权 QQ 扫码。 | 明确账号不匹配，立即关闭目标通道并停止目标，错误账号从未接入 Agent。 |
| P2-05 | 等待扫码时取消；分别注入目标启动失败和旧端恢复失败。 | 先确认目标停止再恢复旧端；恢复失败显示 needs_attention 或明确旧内核待处理，不能把“尝试回滚”记作成功；保留两套 profile。 |
| P2-06 | 在停旧端、启动目标、等待扫码及提交前异常终止并重启管理器。 | operation 持久化；不能确认资源归属/停止时标记 needs_attention，阻止另一次切换；核实真实资源后处理。账号占用不能因 TTL、清空进程内锁或重启而释放。 |
| P2-07 | 在 LLBot 停止路径检查进程组，注入父进程先退出但子进程仍活的场景。 | 记录 PID、PGID 和子进程；必须确认整组停止后才启动目标。只看父 PID 消失不算通过；不得批量杀其他 Node 进程。 |
| P2-08 | 切换期间暂停或使实例到期，然后取消；viewer 查询、跨租户查询和缺 CSRF 写请求。 | 取消可用于安全清理，但不得重新拉起旧 QQ 或 Agent；viewer 只读查询不推进/提交；跨租户和无 CSRF 写请求拒绝。 |
| P2-09 | QQ/B站同时有消息时切换，在提交后重新对话。 | 人设、记忆、白名单和 B站数据保留；旧 QQ 未读、在途和结果不明发送不在新内核重发；记录同实例 B站中断起止及 Agent 恢复次数，其他实例不受影响。 |

每项记录代码版本、Node/QQ/内核版本、镜像 digest、operationId、阶段时间、脱敏运行身份、资源清点与实际结果。分别标记自动化模拟、真实容器、真实账号证据；本地 FakeDockerRunner 和 fake LLBot 通过不能填写真机“通过”。没有有效 AT 时保留 P2-01 负例，P2-02 双向真实切换标记阻塞。P2 单实例通过不代表 P3 三实例并发、异常恢复或备份恢复通过。

## 1. 验收范围

用户主流程：

> 创建实例 → 登录 QQ → 配置可用模型渠道 → 选择群白名单 → 开始养鱼。

产品目标还包括“交钱后开通”，但当前创建和续费接口没有支付成功前置，充值为管理员确认流程。测试必须分别记录技术运行链路和支付开通缺口，不把二者混为已完成。

角色视图：

- 普通用户：我的鱼列表 → 一条或多条实例 → 实例详情、扫码、状态、启停、模型渠道与 Bot 控制台。
- 管理员：用户管理 → 用户拥有的实例 → 创建实例、托管和计费管理；全局实例列表显示所属用户。

第一轮优先验证 **NapCat Docker + 平台内置扩展**，先完成 P0 真实容器验证，再做 P1 单实例真实 QQ 闭环。已配置 LLBot 实例保留原内核；LLBot Direct 回归需有效授权。第二轮再测试 B 站和用户上传扩展。

以下已知缺口单独列为阻塞，不作为已实现能力验收：

| 项目 | 当前边界 |
|---|---|
| 桌面 QQ / PMHQ | 可连接已有 PMHQ，但独立 QQ 启动、注入及完整生命周期尚未完成。 |
| SnowLuma 远程扫码 | 尚无已确认可用的远程取码链路。 |
| 用户上传扩展 | Linux 用户、文件、网络和进程执行隔离尚未完成或验收，云端默认闭锁。 |
| 支付开通 | 创建、续费未绑定支付成功；管理员确认充值不等于核验实际付款。 |
| 真实环境 | 真实 QQ、B 站、模型上游及 Linux 多租户运行仍需执行本文验收。 |

## 2. 测试准备

| 准备项 | 具体要求 |
|---|---|
| Linux 环境 | 使用独立测试目录、独立数据目录；不得覆盖 VPS 上已有正式服务。 |
| Node.js | 统一使用 Node 24，记录确切版本。 |
| 包管理器 | npm；LLBot 使用项目指定的 Yarn 4.18.0，确认 Corepack 可用。 |
| 平台账号 | 一个管理员、普通用户 Alice 和 Bob；另配置 viewer/operator 成员角色。 |
| QQ 账号 | 至少一个专用测试 QQ；同时在线的多实例测试使用不同 QQ 账号。 |
| 测试群 | 一个允许互动的群、一个不在白名单的群；仅在获许可的目标发送测试消息。 |
| LLBot 授权 | 平台管理员预先配置有效的 LLBot Direct 授权。 |
| 模型渠道 | 一个真实可用的模型接口，确定实际模型名并设置测试预算。 |
| 浏览器入口 | 管理面可访问；租户控制台域名、Host 路由及反向代理可用。 |
| 数据与证据 | 使用可删除的测试人设、消息和标记；日志、截图、报告必须脱敏。 |

### 2.1 凭据区别

- QQ 号只是指定登录账号，仍需本人手机扫码或确认。
- LLBot `auth_token` 用于协议端授权，应由平台处理。
- 平台自动签发的租户 Relay Key 是 Agent 访问平台 Relay 的本地凭据。
- 用户自带模型 API Key 属于上游模型服务；当前自定义渠道还需 Base URL 和模型名。
- 绑定本地 Relay Key 不代表外部模型 Key 已验证。

不要将真实密码、私钥、Cookie、二维码、完整 API Key 或主密钥写入本文、聊天或测试报告。

## 3. 阶段 A：Linux 环境与自动化测试

### A1. 记录环境

在 VPS 执行以下只读检查：

```bash
uname -a
uname -m
cat /etc/os-release
node --version
npm --version
corepack --version
free -h
df -h
ss -lntp
```

检查并记录：

1. 系统版本、CPU 架构、Node/npm/Corepack 版本。
2. 启动前内存、磁盘和已有监听服务。
3. 管理端口、Relay 端口及租户端口池是否冲突。
4. Linux 使用适配自身架构的 Node；不能复制 Windows `.tools/node` 运行，也不能照搬 `/e/...` PATH。

### A2. 安装各包依赖

以下命令从 Linux 仓库根目录执行：

```bash
npm --prefix packages/qq-agent-core ci
npm --prefix packages/protocol-bili-bridge ci
npm --prefix packages/cloud-manager ci

(
  cd packages/protocol-qq-llbot
  corepack yarn install --immutable
)
```

注意：

- 根目录不是 npm workspace，各包独立安装。
- LLBot 的安装脚本还会安装其 WebUI 前端依赖，记录下载、原生依赖或构建失败的实际原因。
- cloud-manager 的 panel 无依赖安装及独立构建步骤。
- 若 Corepack 或项目指定 Yarn 不可用，先解决工具链问题，不擅自改锁文件绕过。

### A3. 执行检查、测试和构建

逐条执行、分别记录退出码：

```bash
npm run check

npm run llbot:check
npm run llbot:test
npm run llbot:build

npm --prefix packages/protocol-bili-bridge run check
npm run test:all

npm --prefix packages/cloud-manager/panel test
npm --prefix packages/qq-agent-core run test:headless
```

通过标准：

- LLBot 构建生成 `packages/protocol-qq-llbot/dist/llbot.js`。
- 各命令成功退出；失败则记录具体用例、日志及环境依赖。
- Linux 下执行适用的 headless 进程退出测试。
- 不通过删除断言、伪造组件或忽略退出码把失败改记为通过。

覆盖边界：

- 根 `check` 主要检查版本及脚本契约，不等于全项目静态检查。
- 根 `test:all` 依次运行 B 站桥、cloud-manager、核心全量测试，遇失败即停止。
- 根测试不包含独立 LLBot、panel 和 headless 套件，必须单独执行。
- 核心此前因缺便携 QQ/SnowLuma 在版本检查处失败。Linux 是否同样阻塞需要实测；后续未执行的套件标记为“未执行”，可单独运行并单独记录。
- fake 协议和模型测试证明本地契约，不证明真实账号或上游可用。

## 4. 阶段 B：启动隔离测试平台

### B1. 设置测试配置

从仓库根目录设置非敏感配置：

```bash
export CLOUD_DATA_DIR="$PWD/var/linux-acceptance"
export CLOUD_HOST="127.0.0.1"
export CLOUD_PORT="8080"
export CLOUD_RELAY_HOST="127.0.0.1"
export CLOUD_RELAY_PORT="8790"
export CLOUD_ADMIN_USERNAME="acceptance-admin"
```

确认该目录未存放正式数据。管理员密码通过服务器上的安全方式配置，避免写入命令历史。项目不自动加载 `.env`，需要在实际进程环境中设置配置。

启动：

```bash
npm start
```

另开终端检查：

```bash
curl --fail http://127.0.0.1:8080/healthz
curl --fail http://127.0.0.1:8790/health
```

### B2. 浏览器与网络

- 管理面可以先用 SSH 转发访问。
- 租户 Bot 控制台使用 `<slug>.<baseDomain>`，须配置对应解析、Host 路由和反向代理；只转发管理端口不保证租户域名可用。
- 使用公开域名时配置 HTTPS 和相应 Cookie/代理设置。
- 协议端、Relay 和租户内部端口不直接暴露公网。

通过标准：健康检查成功、管理员能登录、无反复崩溃、监听范围正确、租户控制台可通过授权入口访问。

### C11. 多实例配额

当前非管理员创建规则：将该 owner 已拥有的全部实例数，与**本次新建所选套餐**的上限比较。

| 套餐 | 当前上限 |
|---|---:|
| trial | 1 |
| starter | 3 |
| pro | 10 |

验证 trial 创建第一条成功、第二条被拒；使用允许更多实例的套餐验证创建和超限。受邀成员实例不计入拥有数。管理员创建绕过此限制。不要把这些数值理解为各套餐分别累计配额或用户已经购买的额度。

### C12. 权限负例

| 操作 | 预期 |
|---|---|
| Bob 读取 Alice 私有实例。 | 服务端拒绝。 |
| Bob 请求 Alice 的 prepare/start/qrcode。 | 服务端拒绝，协议方法不被调用。 |
| 无会话访问受保护实例接口。 | 返回未认证错误。 |
| viewer 读取状态。 | 允许。 |
| viewer 扫码或启停。 | 拒绝。 |
| operator 操作其被授权且有效的实例。 | 允许。 |
| 普通用户访问管理员页面和 API。 | 页面受限，API 仍独立拒绝。 |
| 暂停或过期实例执行受限启动/扫码。 | 拒绝并显示明确原因。 |

不能仅凭按钮隐藏认定权限正确。接口请求、租户控制台 HTTP、SSE 和 WebSocket 都要检查。

## 6. 阶段 D：真实 QQ 登录与养鱼

### D1. 扫码登录

1. 管理员准备并验证 NapCat Docker 镜像；如测试现有 LLBot Direct 实例，还需配置有效 LLBot 授权。
2. Alice 从“我的鱼”进入目标实例。
3. 输入测试 QQ 号，点击“扫码登录 QQ”。
4. 手机 QQ 扫码确认。
5. 观察状态更新，核对实际账号。

通过标准：

- 普通用户不需要配置协议 Token 或端口；新实例默认 NapCat，已有实例保留其内核配置。
- 二维码正常显示，关闭窗口停止轮询。
- 登录后页面显示在线，扫码成功后及时刷新状态。
- 实际 QQ 号和昵称与目标账号一致。
- 登录过程不泄露平台授权、OneBot token 或 WebUI 密码。

### D2. 登录异常

| 场景 | 预期 |
|---|---|
| 平台未配置授权。 | 无法取码，用户被提示联系平台管理员。 |
| 平台授权无效或校验中。 | 明确区分失败与等待，不无限重复启动。 |
| 二维码过期、用户取消或网络失败。 | 可以重新获取，旧轮询不会残留。 |
| 使用另一个自有测试 QQ 扫码，账号与预期不一致。 | 触发账号不匹配并停止对应协议实例。 |

### D3. 配置模型和群

1. 选择平台模型渠道，或填写自定义渠道地址、API Key 和模型。
2. 核对 Agent 实际请求模型与可用模型一致。
3. 启动实例。
4. 在 Bot 控制台将测试群加入白名单。
5. 选择大肥鱼人设和低频回复档位，优先测试被 @ 唤醒。

当前自定义渠道保存不执行远端连接验证，也不会自动保证 Agent 默认模型匹配。空白名单不默认放行所有群。

### D4. 真实互动

| 编号 | 操作 | 通过标准 |
|---|---|---|
| D41 | 白名单群内 @ 机器人发送普通问题。 | QQ 收到实际回复，后台有对应会话和模型调用记录。 |
| D42 | 连续数轮日常群聊。 | 回复体现配置人设，无明显配置丢失。 |
| D43 | 提供测试昵称或偏好，再进行后续对话。 | 检查记忆形成和后续引用，记录实际表现。 |
| D44 | 未授权群中 @ 机器人。 | 不发送回复。 |
| D45 | 观察机器人自己的消息。 | 不形成自触发回复循环。 |
| D46 | 验证引用和表情等已支持动作。 | 正确发送；失败时有可定位记录。 |
| D47 | 切换回复档位和概率设置。 | 触发判定符合配置，概率模式通过多条消息观察。 |

模型输出有随机性。单条未回复应结合唤醒判定、模型请求及发送记录定位，不能单凭主观表现判断全部链路故障。

## 7. 阶段 E：多实例与租户隔离

准备 Alice 两条鱼、Bob 一条鱼；真实同时在线使用独立 QQ 账号。

| 编号 | 验证内容 | 通过标准 |
|---|---|---|
| E01 | 数据、进程、端口。 | 实例有独立数据目录和租约，活动端口不冲突。 |
| E02 | 修改 Alice 第一条鱼的人设。 | 其他两条不受影响。 |
| E03 | 白名单、记忆、模型配置和日志。 | 不串实例，未经授权无法读取。 |
| E04 | 停止 Alice 第一条鱼。 | 其他两条保持健康并可操作。 |
| E05 | 多条鱼切换扫码及渠道设置。 | 所有请求绑定正确实例 ID。 |
| E06 | 跨租户控制台 HTTP/SSE/WS。 | 服务端拒绝未经授权访问。 |

## 8. 阶段 F：故障与恢复

仅针对可丢弃测试实例实施故障，不终止其他服务。

| 编号 | 操作 | 通过标准 |
|---|---|---|
| F01 | 正常停止、重新启动一条鱼。 | 状态正确，其他实例不受影响。 |
| F02 | 终止一个测试 Agent 或协议子进程。 | 观察守护重启、退避和错误记录，无无限高速重启。 |
| F03 | 正常关闭再启动管理器。 | 用户、实例、配置和端口状态一致；如需手动启动，准确记录。 |
| F04 | 重启 QQ 协议实例。 | 验证 session 恢复；失效时明确要求重新扫码。 |
| F05 | 测试上游超时或返回错误。 | 错误可追踪，无重复发送或无限重试。 |
| F06 | 给实例写入测试标记、备份、修改、恢复。 | 标记恢复，配置和账号资料不串租户。 |
| F07 | 在隔离副本上测试损坏备份或错误主密钥。 | 恢复被拒，原状态不被破坏。 |

备份边界：

- 租户备份不等于整个平台备份，不保证包含完整钱包、账本及平台设置。
- 平台恢复需数据库一致快照、租户数据、备份文件和原主密钥；不能仅复制运行中的 SQLite 主文件而忽略一致性。
- 使用环境变量提供主密钥时，也必须安全保存原密钥。
- B 站独立的 `secret.key` 随对应数据保留。
- 不在正式实例上覆盖恢复，不把备份或解密凭据放进报告。

## 9. 阶段 G：用量、充值与计费

| 编号 | 操作 | 通过标准 |
|---|---|---|
| G01 | 普通及流式模型请求，上游返回 usage。 | 记录真实用量来源，金额与配置价格一致。 |
| G02 | 测试上游不返回 usage。 | 明确标为估算，不冒充精确供应商账单。 |
| G03 | 不同群/实例发起请求。 | 平台、会话、模型和运行归因正确。 |
| G04 | 含图片请求。 | 显示含图片请求总成本，作为总费用子集，不重复累计。 |
| G05 | 上游失败或超时。 | 预占释放，不长期冻结余额。 |
| G06 | 流式中断。 | 按已取得 usage 或估算结算，来源清楚。 |
| G07 | 余额不足、限速、并发超限、模型不允许。 | 明确拒绝，未成功请求不产生错误重复扣费。 |
| G08 | 自定义模型上游。 | 保持不扣平台钱包的现有行为；平台零费用不代表供应商免费。 |

充值验证：

1. 用户选择已有实例并提交充值申请。
2. 申请处于 pending，钱包余额不增加。
3. 管理员确认后检查到账。
4. 重复确认同一申请不得重复入账。

当前创建、续费没有支付前置，管理员确认也不自动核验实际付款。这是商业上线缺口，不能记为“支付自动开通已通过”。

## 10. 第二轮：B 站与扩展

### 10.1 B 站

QQ 主链路通过后，使用授权的测试目标验证：

- 扫码、登录状态、重启恢复及 Cookie 保活。
- 视频评论、动态回复、私信、UP 订阅和直播。
- 动态评论使用正确业务类型和目标 OID，楼层关联正确。
- watcher 开关实际控制轮询，停用状态在重启及状态文件异常后保持合理行为。
- 视频上下文在唤醒时获取，缓存有效，失败和缺字幕能降级。
- 单张私信图片真实上传并发送；当前支持范围为不超过 5 MiB 的 PNG/JPEG/GIF。
- 评论和直播图片等不支持场景明确拒绝，不反复重试。
- QQ 和 B 站目标、消息和发送动作不串通道。
- 触发真实平台风控时停止并记录，不制造重试风暴。

### 10.2 用户上传扩展

第一轮保持默认关闭。完成并验收 Linux 用户、文件、网络和进程隔离后，再在隔离测试环境验证：

1. 可信 ZIP 上传、清单校验及加载。
2. 实际调用扩展工具。
3. 禁用后工具和定时任务退出。
4. 安装失败、热重载失败能够回滚。
5. 路径穿越、超限压缩包和跨租户访问被拒绝。
6. A 租户扩展不能读取或影响 B 的数据和进程。

`QQ_AGENT_EXTENSION_ISOLATION_CONFIRMED=1` 只是部署声明，不创建沙箱，也不能作为隔离通过证据。

## 12. 第一轮通过条件

以下条件全部满足，才可将第一轮标记为“Linux 基本养鱼链路通过”：

- [ ] 管理员可按用户查看和管理实例。
- [ ] 普通用户可查看并管理自己的一条或多条鱼。
- [ ] 至少一条鱼完成真实扫码、模型调用和白名单群回复。
- [ ] 跨租户请求被服务端拒绝，viewer/operator/owner 权限正确。
- [ ] 正常重启和单实例故障不会影响其他实例。
- [ ] 模型用量、错误和发送记录可追踪。
- [ ] 自动化测试结果完整记录；环境阻塞和未执行项没有误记为通过。
- [ ] 测试进程和临时资源清理结果已确认。

通过第一轮不等于完整商业上线。支付校验、未实现协议能力、执行隔离及其他未通过项须单独关闭。
